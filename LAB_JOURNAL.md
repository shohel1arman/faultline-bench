# Lab journal

One entry per working day. Each entry: planned / done / problems / next.
Deadlines (AoE): registration Nov 10, paper Nov 16, supplementary Nov 23, 2026.

## 2026-10-14

**Planned**
- Set up repository and project structure.
- Decide data sources; build the conflict generation pipeline.

**Done**
- Repository scaffold, config, README.
- Data sources checked: GQA scene graphs (sceneGraphs.zip, 42.7 MB) and Visual Genome
  image metadata (image_data.json.zip, 17.6 MB); both CC BY 4.0 per their download pages.
- Generation pipeline: candidate extraction, geometric relation check, typed and graded
  edits, MCQ options, controls with foils, quota assignment, schema validation.
  17 unit tests on synthetic scene graphs; end-to-end smoke build on 3,000 synthetic images.
- Construction rules written up in docs/DATASET.md.

**Decisions**
- Images come from Visual Genome, not COCO val2017 directly. GQA bounding boxes are in VG
  pixel coordinates, so VG images keep boxes and images consistent. Many VG images are COCO
  images; the COCO id is kept in each record where available.
- Only the GQA *validation* scene graphs are used, to reduce overlap with GQA training
  data that open VLMs commonly see.
- Relations are restricted to 2D spatial relations (left of, right of, above, below) and are
  re-verified from bounding boxes, so every relation conflict is geometrically checkable.
- People are excluded as targets and as replacement objects (avoids gender/identity edits).
- No closed-model APIs. All evaluation runs on open models on Kaggle T4.

**Problems / risks**
- Scene graphs are incomplete: a replacement object marked absent might still be visible.
  The human verification pass checks this.
- S3 colour edits (e.g. red to orange) may be ambiguous for humans too; the verification
  pass decides whether S3 survives.

**Problems found while building**
- Colour distractors could be near the true colour (beige vs tan), making MCQ ambiguous.
  Distractors now exclude near colours of the true answer.
- Some object pairs were hypernyms (taxi/car, duck/bird, mug/cup, desk/table,
  monitor/television, sign/stop sign); removed from the vocabulary.

**Next**
- Run download + build on real GQA val data; check cell supply against the 400+60 quota.
- Read 50 generated samples with their images before fetching all images.

## 2026-10-15

**Planned**
- Evaluation harness for small open VLMs on the available hardware.

**Done**
- Compute changed: Kaggle and the shared lab server are not used. Runs are on a Windows PC
  with two RTX 2060 (6 GB each, no bfloat16). This replaces the Kaggle plan of 2026-10-14.
- Harness: seven probes per record plus a verbalize-then-answer follow-up; multiple choice
  scored from option-letter probabilities instead of generation; outputs appended per
  record with automatic resume and retry of failed records.
- Parsing and scoring kept separate from running, so parser fixes never need a rerun.
- Model list (2B to 4B, four families, all fit one 6 GB GPU at 4-bit): Qwen2.5-VL-3B,
  Qwen3-VL-4B, InternVL3-2B, SmolVLM2-2.2B. Ids checked on the Hugging Face model pages.
- Checked against transformers 5.19 source: AutoModelForImageTextToText covers all four;
  processors take text and images as keywords; BitsAndBytesConfig arguments.
  The PyPI torch build (2.14.1, CUDA 13.0) includes sm_75 kernels for the RTX 2060.
- 35 unit tests, including a fake text-following model run end to end and a stub model
  for letter scoring. Real models could not be run here (no GPU, model hub not reachable),
  so the first real check is the 5-record smoke test.
- docs/EVAL.md (probes and metrics) and docs/RUNNING.md (setup and long runs).
- Switched the setup from WSL2 to native Windows: torch comes from the PyTorch cu130 index
  (PyPI has only CPU builds for Windows, per the uv PyTorch guide); bitsandbytes ships
  Windows wheels with sm_75 (per its installation page). All text files are read and
  written as UTF-8 with LF endings, and scripts print UTF-8, so outputs are identical
  across Windows and macOS. .gitattributes keeps LF in the repo.
- uv.lock removed for now: the lock must include the cu130 index, which this sandbox
  cannot reach. It is regenerated by the first sync on the Windows PC and committed.

**Decisions**
- Same precision for every model: NF4 weights, float16 compute.
- Images downscaled to longer side 672 px for every model.
- Added `ResA_mcq_if_perceived`: resolution measured only on records the model gets
  right from the image alone, so perception failures are not counted as trusting the text.
- Added an instruction baseline (`mcq_focus`, "rely on the image") alongside verbalize.
- No 7B+ or 32B models: the paper states the 2B to 4B scope as a limitation.

**Problems / risks**
- Some models may overflow in float16; the harness records non-finite logits as errors.
- Detection and attribution parsing is heuristic; unparsed rates are reported and a sample
  of outputs will be checked by hand.

**Next**
- Windows setup, dataset build, 5-record smoke test per model; record seconds per record.

**First real build (Mac mini, GQA val, 10,696 images)**
- 4,033 records, all valid. Seven of nine conflict cells full (400 + 60). Problems:
  object S3 got 77 of 460 although 1,705 candidates existed; object controls 0,
  relation controls 122 of 154.
- Cause: the cell-by-cell greedy fill. Object S1/S2 (far edit) and S3 (near edit) come
  from the same 1,705 objects, and relation cells draw on a superset of them, so cells
  filled first used up objects that later cells (object S3, controls) needed.
- Real limit underneath: object and relation samples both need an anchor; 2,915 objects
  qualify, and object + relation quotas ask for 3,068. Main quotas alone need 2,668.

**Fix**
- Replaced the greedy fill with a max-min fair allocation using augmenting paths (main
  quotas first, then reserves; random main/reserve split). On synthetic data with the
  same overlap structure it assigns the same total as the greedy but spreads shortages
  evenly (greedy left attribute S2 at 18 of 400 and controls at 0; the new allocation
  gives every cell about 65%). With enough supply both fill everything.
- Build report now lists distinct objects per type and the object + relation demand.
- 42 tests, including allocation validity, even spreading under shortage, main before
  reserve, and identical output across Python hash seeds.
- Expected on the real data: all main cells and controls full; object and relation
  reserves somewhat below 60. To be confirmed by rerunning the build on the Mac.

**Second build (after the allocation fix)**
- 4,062 records, 3,044 images. Core subset complete and balanced: 200 per cell and 67
  controls per question type (2,001 items). Attribute cells full (400 + 60).
- Object and relation cells reach 379 main each, controls 127, no reserves. The limit is
  the two-samples-per-image cap: objects that qualify for object or relation samples are
  concentrated in the same images.
- Decision: accept and freeze this build as v0. Every model runs the core set; the main
  set only adds precision. Reserves are not needed: the 500-item human check estimates
  the error rate, and wrong items it finds are dropped and reported, not replaced.
  Not raising the per-image cap to 3 avoids more within-image correlation.
- The dataset file and its stats are committed so every run uses identical records.
- Added scripts/preview.py: an HTML page with two samples per cell, image, target and
  anchor boxes and the edited span, for a manual check before any model runs.

**Images**
- Per-image Visual Genome URLs (cs.stanford.edu) refuse connections from the Mac
  ("Connection refused"), while downloads.cs.stanford.edu works.
- New default image source: the GQA images.zip on downloads.cs.stanford.edu, which holds
  the same Visual Genome images named by image id. faultline/remote_zip.py reads the zip
  index and only the needed members with HTTP range requests (about 0.5 GB instead of the
  whole archive), checks each member's CRC, and handles Zip64. 6 new tests on in-memory
  archives; the real server's range support is checked at start-up.

**First smoke test (InternVL3-2B, Mac mini, macOS 14.6)**
- Model downloaded and loaded (3.9 GiB on the Apple GPU), then the process aborted in the
  first linear layer: "-[MPSNDArray arrayViewWithShape:strides:]: unrecognized selector".
  The installed torch was 2.15.0. The PyTorch 2.14 MPS notes give macOS 14 as the minimum;
  a secondary report says 2.15 needs macOS 15. The error (a missing Apple GPU function) is
  consistent with that; not confirmed in PyTorch's own documentation.
- Fix: pin torch below 2.15 on macOS only; run_eval.py now stops with a clear message if
  torch 2.15+ meets macOS older than 15. The lock file is regenerated on the Mac.

**Second smoke test (InternVL3-2B, torch < 2.15)**
- Runs end to end on the Apple GPU. About 4 to 6 s per image probe and 0.1 s for the
  text-only probe, so about 32 s per record: roughly 18 h for the 2,001-record core set.
- First qualitative signal of the target effect: on an airplane colour conflict the model's
  detection answer names the error ("the image shows a red airplane") while its open answer
  follows the text ("blue"), and its structured attribution contradicts its own detection
  ("Error: no", "Wrong input: image").
- Dataset problem found: a cow labelled only "white" in the scene graph is black and white
  in the image, so the colour question had no single right answer. Animal coats are often
  patterned. Rule added: colours of animals are never edited or stated (attribute targets,
  relation subjects, filler sentences). The dataset is rebuilt before any full run; the
  smoke-test outputs are discarded because record ids change.
